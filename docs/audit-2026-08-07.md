# Audit — 2026-08-07 (v0.6.0)

Findings from two independent reviews of the repository at `047cdf4`, plus the
verification I ran against the actual Zigbee2MQTT **2.12.1** source before
accepting any claim about the bridge API.

Ground truth was read from a live install at `/opt/zigbee2mqtt/dist` rather than
from documentation or memory, because several findings contradict our own
descriptions.

Status: `[x]` fixed in this pass, `[ ]` deferred with a reason.

---

## Why these got through

Every defect below lives in one layer: **the bridge request payloads in
`src/tools.ts`**. Of 24 tool handlers, only `z2m_connection_status` had any
behavioural test. The rest were exercised solely through confirmation-gate tests
using a client that throws on contact, so **not one request sub-topic or payload
key was asserted anywhere in the suite**.

The mutation harness inherited the same blind spot: 27 of 29 mutants target
`devices.ts`, `topics.ts`, `redact.ts` and `config.ts`, and the two that touch
`tools.ts` are both confirmation gates.

So a green suite, a full mutation sweep and a passing live smoke test could all
coexist with a tool that had never once succeeded. The fix is a payload
assertion layer, not more of the same tests.

## Blocker

### B1 — `z2m_bind` with `action: "clear"` has never worked

- [x] Fixed

We send `{ id: <device> }`. Zigbee2MQTT requires `target`:

```js
// extension/bind.js:279
if (typeof message !== "object" || typeof message.target !== "string") {
    await this.publishResponse("binds/clear", message, {}, "Invalid payload");
```

Every call returns `Invalid payload`. The error gives a model nothing to correct
with, so it retries the same call. Also adds the optional `ieee_list` that
Zigbee2MQTT accepts (defaults to `["0xffffffffffffffff"]`, meaning all).

## High

### H1 — The `/ENDPOINT` suffix does not exist

- [x] Fixed

`z2m_bind` and `z2m_manage_group` told the model to write `my_remote/left`.
`bind.js` calls `resolveEntity(message.from)` — not `resolveEntityAndEndpoint` —
and reads separate keys:

```js
// extension/bind.js:220-225
const sourceEndpointKey = message.from_endpoint ?? "default";
const targetEndpointKey = message.to_endpoint;
const resolvedSource = this.zigbee.resolveEntity(message.from);
```

`groups.js` reads `message.endpoint`. So endpoint-scoped binding — the main
reason to bind at all, e.g. one button of a multi-button remote — could not be
expressed. Adds `from_endpoint`, `to_endpoint` and `endpoint`, and removes the
false guidance.

### H2 — Touchlink could factory-reset the nearest device

- [x] Fixed

The handler built a target only when `ieee_address && channel !== undefined`,
and otherwise sent `{}`. Zigbee2MQTT treats an empty payload as "reset whatever
you find first":

```js
// extension/bridge.js:389-391
else {
    logger.info("Start Touchlink factory reset of first found device");
    result = await this.zigbee.touchlinkFactoryResetFirst();
}
```

A model supplying `ieee_address` but omitting `channel` therefore triggered an
irreversible factory reset of a physically nearby device — exactly the hazard
the tool's own description warned about. Partial targets are now rejected, and
the untargeted form requires an explicit `nearest: true`.

### H3 — `clear_cache` was silently ignored

- [x] Fixed (parameter removed)

`grep -rn clear_cache /opt/zigbee2mqtt/dist` returns nothing. `removeEntity`
reads only `block` and `force`. We advertised "discard cached data so a rejoin
re-interviews from scratch" and reported success for a no-op.

### H4 — A broker drop could spawn a duplicate client with the same client ID

- [x] Fixed

`connect()` returned early only when `client.connected` was true. During
mqtt.js's own reconnect window that flag is false and `connectPromise` is null,
so the next tool call dialled a second client and overwrote `this.client`
without ending the first. The orphan kept reconnecting forever using an
identical client ID, so the broker evicted one of the pair repeatedly. The
client now tracks its own connection state and lets mqtt.js recover.

### H5 — `publish()` could hang forever

- [x] Fixed

The promise settled only on the QoS 1 acknowledgement. If the broker never
acknowledged, it never settled. `request()` had a timeout; `publish()` — which
backs `z2m_set_state`, the tool that operates locks, valves and sirens — had
none.

## Medium

### M1 — `permit_join_end` was reported 1000x in the future

- [x] Fixed

zigbee-herdsman stores milliseconds since the epoch
(`this.permitJoinEnd = Date.now() + timeMs`), and we multiplied by 1000 again.
"Is the network still open for pairing?" returned a date roughly 56,000 years
out.

### M2 — Numeric arguments were coerced, never validated

- [x] Fixed

`Number("ten")` is `NaN`, and nothing checked. `limit: "ten"` produced
`slice(0, NaN)` and an empty device list, which reads to a model as an empty
estate. `timeout_ms: "fast"` produced `setTimeout(NaN)`, coerced to 0, an
instant timeout. `config.ts` already validated environment integers strictly;
the same rigour was missing at the tool boundary.

### M3 — No payload ceiling anywhere

- [x] Fixed

`z2m_list_devices` had no default limit, `z2m_network_map` no cap, and
`include_config` returned the entire `configuration.yaml`. On a large estate a
single tool result could exhaust a model's context window. Adds a default
limit, a node cap, and a byte guard that truncates with an explicit marker
rather than returning a wall of JSON.

### M4 — `z2m_check_updates` had no total budget

- [x] Fixed

A sequential loop over every router at 60 s each: up to ~25 minutes in one call
on a 50-device estate. Every MCP client times out long before, and the loop
keeps running with no way to stop it. Adds `max_devices` and an overall
deadline, and returns what remains so the model can continue deliberately.

### M5 — README claimed Zigbee2MQTT 1.17+ compatibility

- [x] Fixed

Several tools need 2.x: `bridge/health`, `device/reporting/configure`,
`device/binds/clear`, the OTA schedule topics and `interview_state`. On 1.17
those time out with no explanation.

### M6 — `summariseExposes` dropped the value ranges it promised

- [x] Fixed

It emitted `brightness:numeric` and nothing else, while `z2m_get_device`'s
description said to call it "to discover valid values". A model could not learn
that `brightness` is 0-254 without setting `include_raw`.

### M7 — `deviceState` and `availability` grew without bound

- [x] Fixed

`logs` and `events` were capped and tested; these two were not. Every rename
leaves the old key behind, and any third party publishing under the base topic
mints entries. Now pruned against `bridge/devices`.

## Low

- [x] **L1** — connect-error path never cleared its timeout handle, delaying exit.
- [x] **L2** — every mqtt.js reconnect started another `waitForBridgeData` poll.
- [x] **L3** — `JSON.stringify(undefined)` returned `undefined` as tool text.
- [x] **L4** — no `unhandledRejection` / `uncaughtException` handler, so a throw
  inside the message listener killed the session with no diagnostic.
- [x] **L5** — `z2m_check_updates` filtered on `type === "Router"` while the
  schema said "all mains-powered devices".
- [x] **L6** — `Z2M_MQTT_CLIENT_ID` was supported but undocumented.
- [x] **L7** — `z2m_permit_join` documented a 254 s maximum and never enforced it.
- [x] **L8** — `server.json` marked `Z2M_MQTT_URL` as `isSecret: false` although
  it routinely carries `user:pass@`, contradicting our own threat model.
- [x] **L9** — README said "three safe tools reduce state" and named two.

## Not fixed here — product gaps

These are feature work, not defects, and belong in a roadmap discussion rather
than a bug-fix release.

| Gap | Bridge topic | Why it matters |
| --- | --- | --- |
| Backup | `bridge/request/backup` | The one thing a cautious admin wants before letting an assistant near the mesh. No competitor has it. |
| OTA progress polling | `update.progress` in `bridge/devices` | `z2m_ota_update` blocks for up to 30 minutes, so a firmware campaign is unusable end to end. |
| Install codes | `bridge/request/install_code/add` | Zigbee 3.0 QR-code devices cannot be paired at all without it. |
| Scenes | `scene_add`, `scene_recall`, ... | `z2m_list_groups` shows scenes but nothing can act on them. |
| Device replacement | composite | Nothing captures a dead device's groups, bindings, reporting and options. |
| Cluster discovery | `bridge/definitions` | `z2m_bind` needs exact strings like `genLevelCtrl`; nothing tells the model what is valid. |
| Group options | `bridge/request/group/options` | The device equivalent exists; the group one does not. |
| Disable a device | `device/options` `{disabled: true}` | `z2m_remove_device` says "prefer disabling" and offers no way to do it. |

Also open, and worth a decision rather than a patch: `z2m_set_state` sits in the
`safe` tier, so a default install can operate door locks and valves. It is
documented in three places, but "safe" is doing double duty as both "reversible"
and "routine".
